# Telegram Chat Stats — спецификация

## 1. Что это

Десктопное приложение для анализа экспортов переписки Telegram. Пользователь скармливает `result.json` (экспорт Telegram Desktop), приложение считает статистику и показывает её в виде дашборда и «слайдов» в духе годовых итогов, которые можно выгрузить картинками и отправить в чат.

Инструмент **универсальный**: он ничего не предполагает про конкретный чат.

## 2. Область применимости

Приложение должно одинаково корректно работать на всём диапазоне входных данных:

- **По объёму** — от пары сотен сообщений до нескольких миллионов
- **По периоду** — от чата, которому три дня, до чата, которому пятнадцать лет
- **По числу участников** — личная переписка на двоих, группа из пяти человек, супергруппа на тысячу
- **По типу** — например, `personal_chat`, `private_group`, `public_supergroup`, `private_supergroup`, `saved_messages`, `bot_chat` (тип лежит в поле `type` в корне экспорта). Список неполный — Telegram Desktop добавляет новые значения между версиями, парсер не валидирует `type`, а передаёт как есть
- **По языку** — интерфейс и словарные метрики не привязаны к русскому

Это не «фича на будущее», а требование к каждой метрике и каждому экрану. Метрика, которая красиво выглядит на десяти годах и разваливается на трёх днях, считается недоделанной — см. §7.

## 3. Мультичатовость

Приложение работает с **библиотекой импортов**, а не с одним файлом.

- Пользователь может импортировать сколько угодно выгрузок, они хранятся одновременно
- Между чатами можно свободно переключаться; статистика каждого сохраняется и не пересчитывается заново при возврате
- У каждого чата своя карточка в библиотеке: название, тип, период, число сообщений и участников, дата импорта, размер исходного файла
- Каждый импорт независим: своя таблица участников, свои слияния дублей и скрытые боты, свои настройки отображения. Настройки одного чата не протекают в другой
- Импорт можно удалить — вместе со всеми производными данными
- Повторный импорт того же чата (свежая выгрузка спустя время) **обновляет** существующий, а не создаёт второй. Опознание — по `id` из корня экспорта. Если `id` отсутствует в старых версиях экспорта, спросить пользователя явно: обновить существующий или создать новый
- Активный чат запоминается между запусками приложения
- Сравнение чатов между собой в первой версии не делаем, но схема данных не должна этому мешать

## 4. Жёсткие ограничения

1. **Полностью офлайн.** Ни одного сетевого запроса в рантайме. Никакой телеметрии, аналитики, шрифтов с CDN, обновлялок. Данные не покидают машину пользователя — это не «фича», это главное требование, ради которого приложение вообще десктопное.
2. Все зависимости вендорятся в бандл (шрифты, иконки, словари стоп-слов, стеммеры).
3. CSP в `tauri.conf.json` запрещает любые внешние origin.
4. Работа при полностью отключённой сети — часть приёмки.

## 5. Стек

- Tauri 2 (Rust backend)
- React 18 + TypeScript, Vite
- SQLite через `rusqlite` (feature `bundled`) — хранилище распарсенных данных
- `serde` / `serde_json` — стриминговый парсинг
- `rust-stemmers` — стемминг (Snowball, много языков, включая русский и английский)
- `whatlang` или аналог — определение языка чата
- Charts: recharts (обычные графики), d3-force или sigma.js (граф ответов)
- `html-to-image` + Tauri fs plugin — экспорт слайдов в PNG

## 6. Архитектура

Тяжёлая работа целиком в Rust. React только рисует.

```
result.json ──[стриминговый парсер, Rust]──> SQLite (app data dir)
                                                │
                                    [SQL-агрегаты, Rust]
                                                │
                                    Tauri commands (JSON)
                                                │
                                        React: дашборд + слайды
```

**Почему так.** Экспорт крупного чата — от сотен мегабайт до нескольких гигабайт. Читать его в webview нельзя: память и заблокированный UI-поток. Rust читает файл потоково, никогда не держа в памяти весь JSON, и складывает в SQLite. Дальше все метрики — это SQL-запросы, которые отрабатывают за миллисекунды, поэтому UI мгновенно переключает фильтры (период, участник, чат).

Все импорты живут в **одной** базе; `chat_id` — обязательная часть ключа везде. Это упрощает бэкап и переключение между чатами, а изоляция обеспечивается на уровне запросов. Каждый запрос обязан фильтровать по `chat_id`; отсутствие такого фильтра — баг, даже если сейчас чат один.

### Импорт

- Парсинг потоковый: **нельзя** делать `serde_json::from_reader::<Value>`. Нужен кастомный `Visitor` на поле `messages`, который десериализует элементы по одному. Альтернатива — крейт `struson` (pull-парсер). Пиковая память импорта — цель < 300 МБ независимо от размера файла.
- Запускать в `tauri::async_runtime::spawn_blocking`, прогресс слать событием `ingest://progress` (обработано сообщений, оценка общего числа, ETA)
- Импорт можно отменить, отменённый импорт не оставляет мусора в базе
- Вставки батчами по ~5000 в одной транзакции, `PRAGMA journal_mode=WAL`
- Индексы строим **после** заливки данных, не до
- Маленький файл должен импортироваться мгновенно: не показывать прогресс-модалку, если импорт занял меньше секунды

### Схема БД (ориентир, не догма)

```sql
chats(id, tg_chat_id, name, type, source_filename, imported_at,
      first_msg_ts, last_msg_ts, message_count, detected_language)
people(id, chat_id, tg_id, display_name, merged_into, is_hidden)
aliases(person_id, name, first_seen, last_seen)   -- имена меняются со временем
messages(id, chat_id, tg_msg_id, person_id, ts, text, text_len, word_count,
         reply_to, forwarded_from, via_bot, media_type, duration_sec,
         sticker_emoji, is_edited, is_service, action)
reactions(chat_id, message_id, emoji, count, from_person_id)
links(chat_id, message_id, domain, url)
tokens(chat_id, message_id, person_id, bucket, lemma)
```

Миграция `0004` реализовала часть `messages` под «Типы сообщений» чуть иначе: `forwarded_from`/`media_type`/`duration_seconds` как здесь, но `edited_ts` вместо `is_edited` (сразу значение, не флаг) и отдельные `has_photo`/`has_file`/`has_poll`/`has_location`/`has_contact` — эти поля в реальном экспорте не имеют общего `media_type`, лежат в `extra` (model.rs), других способов их узнать нет. `chats.message_types_ready` (не показан выше) — флаг «эта строка прошла через актуальный импортер», отличает «медиа не было» от «ещё не посчитано» после апдейта (§7). `tokens` — самая большая таблица, её можно строить лениво (по кнопке «посчитать словесную статистику»), чтобы первый импорт был быстрым.

Реакции (Фаза 6) тоже разошлись со схемой-ориентиром: вместо одной таблицы `reactions(chat_id, message_id, emoji, count, from_person_id)` миграции `0008`–`0010` завели три — `message_reactions` (по строке на тип реакции на сообщении), `reaction_actors` (по строке на известного реагировавшего, `recent` в экспорте Telegram усечён) и `message_reaction_previews` (текст сообщений с реакциями, снятый один раз при импорте — `messages.text` в реализации не хранится вовсе). Подробности — `CLAUDE.md`/`docs/PLAN.md` Фаза 6.

## 7. Адаптивность к масштабу данных

Ключевое требование универсальности. Реализуется двумя механизмами.

**Гранулярность времени выбирается автоматически** по длине выбранного периода: часы → дни → недели → месяцы → годы. Слайдер периода тоже подстраивается: у чата за три дня это выбор часов, у чата за десять лет — выбор лет. Никаких зашитых «по годам».

**У каждой метрики объявлены требования** к данным: минимум сообщений, минимальный период, минимум участников, наличие опциональных полей в экспорте. Если требование не выполнено, метрика не показывается вовсе или показывается с честной пометкой «мало данных» — но никогда не рисует пустой или бессмысленный график. Примеры:

- «Слово периода» требует как минимум двух сравнимых интервалов и порога частоты; на трёхдневном чате не показывается
- Граф ответов бессмысленен для личной переписки на двоих — заменяется на метрики диалога (баланс инициативы, время ответа)
- «Топ участников» в переписке на двоих вырождается — вместо рейтинга показываем соотношение
- Реакции есть только в свежих версиях экспорта — при отсутствии поля метрика скрывается, а не показывает нули

## 8. Особенности формата экспорта (важно, здесь все спотыкаются)

1. Поле `text` бывает **строкой ИЛИ массивом** из строк и объектов (`{type: "link", text: "..."}`, `mention`, `bold`, `code`...). Надёжнее использовать `text_entities` и склеивать `text` из элементов. Нужен кастомный `Deserialize`.
2. Идентификация людей — **только по `from_id`** (вида `user123456789`), никогда по `from`: отображаемое имя со временем меняется. `from` собираем в `aliases`.
3. `type: "service"` — входы/выходы, смены названия чата, закрепления, звонки. Исключать из счётчиков сообщений, но сохранять: история названий чата — отдельная метрика.
4. `date_unixtime` надёжнее строкового `date`. Часовой пояс — локальный у того, кто экспортировал; в UI это надо честно оговорить, потому что «активность по часам» от него зависит.
5. Поля присутствуют не всегда и зависят от версии Telegram Desktop: `reactions`, `edited`, `via_bot`, `duration_seconds` могут отсутствовать. Всё опциональное. Приложение не падает на старых экспортах — только помечает метрику недоступной.
6. Медиа обычно не выгружаются, но метаданные есть: `media_type`, `duration_seconds`, `sticker_emoji`, `mime_type`.
7. Личная переписка и группы устроены по-разному: в `personal_chat` нет служебных сообщений о вступлении, зато бывают звонки и `actor` вместо `from`.
8. Удалённые аккаунты приходят как `"Deleted Account"` с разными `from_id`.
9. Каналы и боты в выгрузке встречаются как участники — их нужно уметь скрывать.

### Тестовые данные

В `tests/fixtures/` лежит **набор** синтетических экспортов, покрывающих не только краевые случаи формата, но и краевые масштабы: трёхдневный чат, личная переписка на двоих, группа на 50 человек, чат без реакций (старая версия экспорта), чат на английском. Каждая метрика тестируется на всём наборе. Реальные экспорты в репозиторий **не коммитятся никогда**.

## 9. Метрики

Все метрики считаются в границах выбранного периода и выбранного чата. У каждой объявлены требования из §7.

### Базовые
- Всего сообщений / слов / символов; график активности в автоматической гранулярности
- Топ участников — за весь период и по интервалам (видно смену эпох)
- Средняя и медианная длина сообщения на человека
- Тепловая карта «день недели × час», общая и персональная
- Рекордный интервал активности; самая долгая тишина
- Кто чаще редактирует сообщения

### Социальная динамика
- Граф ответов по `reply_to`: рёбра — кто кому отвечает чаще, чем ожидалось бы при случайном распределении (не сырые счётчики — иначе граф просто отражает общую активность). Для чатов на двоих заменяется на метрики диалога.
- Медианное время ответа на человека
- Кто заводит разговор (первое сообщение после паузы) и кто его хоронит. Порог паузы вычисляется от плотности чата, а не зашит константой
- Реакции: кто получает, кто ставит, кто чей фанат; самое залайканное сообщение
- Самый длинный монолог без ответа

### Язык
- «Слово периода»: слова с аномальным скачком частоты в конкретном интервале. Считать через log-odds ratio с информативным приором (Monroe et al.), не через сырые доли — иначе наверх вылезает случайный мусор. Порог минимальной частоты обязателен.
- «Слово-визитка» участника: TF-IDF по людям
- Топ эмодзи и стикеров на человека
- Индексы: смешливость, капслок, мат

Язык определяется по содержимому чата, стеммер и стоп-слова выбираются под него. Пользователь может переопределить язык вручную. Для неподдерживаемого языка словарные метрики отключаются, остальные работают.

### Типы сообщений

Универсальный блок — одна раскладка на любой счётный тип сообщения: переключатель типа со счётчиком → карточка (всего/% от всех сообщений + 3 ячейки сводки, свои для частотных типов и для типов с длительностью) → гистограмма → таблица участников. 13 типов: `text` (непустой `text_len` — не эксклюзивен с медиа: фото с подписью считается и в `photo`, и в `text`), `photo`, `sticker`, `voice_message`, `video_message` («кружочек»), `video_file`, `animation`, `file` (документ без узнанного `media_type`), `forwarded` (`forwarded_from`), `edited`, `poll`, `location`, `contact`. Голосовые/кружочки получают вариант с длительностью (суммарно/медиана/самое длинное) вместо частоты/пика/лидера — метрика приносит свои дополнения, раскладка остаётся одной. Реакции не входят в этот блок — им нужна отдельная таблица `reactions` (сообщение может собрать реакции от многих людей), это метрика раздела «Социальная динамика» выше, не универсального блока.

Гистограмма — три вида, не одна временная шкала: «по месяцам» — абсолютный календарный бакет, временной ряд как у графика активности; «по дням» — распределение по **дню недели** (Пн–Вс), не по календарной дате — то же сообщение раз в неделю по понедельникам схлопывается в один бакет, а не размазывается на N разных дат; «по часам» — распределение по часу суток (0–23), тоже агрегат за весь период, не временной ряд. Это осознанно другая, более простая гранулярность, чем пятиуровневая `Granularity` графика активности (§7) — «по дням»/«по часам» здесь всегда доступны, «по месяцам» скрывается на слишком коротком периоде. «Пик» и «средний темп» в карточке сводки считаются по абсолютному календарному бакету (месяц или день) независимо от того, какой из трёх видов сейчас выбран для самой гистограммы — «пик по дню недели» не имеет смысла как понятие.

Требования §7: тип с нулём вхождений в чате — пилюля неактивна, но остаётся в списке; тип, для которого экспорт вообще не содержит нужных полей (старый Telegram Desktop) — весь блок деградирует в «Обновить выгрузку», а не показывает лживые нули.

### Медиа и прочее
- Голосовые: суммарная длительность на человека, рекорд — базовая версия уже покрыта раскладкой «Типы сообщений» выше (карточка voice_message); здесь остаётся то, что не помещается в общий переключатель типа
- Топ доменов в ссылках
- Откуда чаще всего репостят (`forwarded_from`) — базовый счётчик пересланных на человека уже в «Типы сообщений»; здесь — именно top источников (`forwarded_from` как значение, а не факт пересылки)
- История названий чата, входы и выходы

### Интерактив
- «Угадай, кто написал»: случайное сообщение, варианты авторов, счёт

Метрики независимы. Каждая — отдельный модуль, который можно выключить. Порядок реализации: базовые → медиа → социальные → языковые.

## 10. Экраны

1. **Библиотека** — список импортированных чатов карточками, кнопка нового импорта, удаление и обновление существующих. Стартовый экран, если импортов больше одного.
2. **Импорт** — дроп-зона, инструкция по выгрузке из Telegram Desktop, прогресс с ETA и отменой, обработка ошибок формата
3. **Люди** — список найденных `from_id` с алиасами; слияние дублей, скрытие ботов, назначение отображаемых имён. Своё состояние на каждый чат.
4. **Дашборд** — метрики, выбор периода, фильтр по участникам, переключатель чата доступен не выходя на библиотеку
5. **Слайды** — полноэкранные итоги с навигацией, общие и персональные. Заголовок и разбивка зависят от периода: у долгого чата это годы, у короткого — дни. Никаких зашитых «Итоги года».
6. **Экспорт** — рендер слайдов в PNG в выбранную папку

## 11. Производительность (цели)

- Импорт 1M сообщений: < 3 мин, память < 300 МБ
- Импорт маленького чата: мгновенно, без модалок
- Любой запрос дашборда: < 200 мс
- Переключение периода и переключение между чатами: без видимой задержки

## 12. Чего не делать

- Не тянуть сетевые библиотеки, шрифты, аналитику
- Не грузить весь JSON в память
- Не считать метрики в JS
- Не зашивать предположения о масштабе, языке, типе чата и числе участников
- Не писать запросы без фильтра по `chat_id`
- Не коммитить реальные данные чата ни в каком виде
