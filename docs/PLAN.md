# План разработки

Верхнеуровневый план по фазам, в порядке зависимостей. Каждая фаза — один или
несколько вертикальных срезов; перед стартом каждого показывается план и
ждётся подтверждение (см. CLAUDE.md «Как я хочу работать»). Порядок фаз 0–3
жёсткий: без импорта и людей метрикам считать не над чем. Порядок 4–7 внутри
себя подвижный и совпадает с `docs/SPEC.md` §9 («базовые → медиа →
социальные → языковые»).

Статус: 🔲 не начато · 🔶 в работе · ✅ готово

**MVP-срез (сентябрь 2026).** По просьбе пользователя увидеть рабочий MVP
раньше, чем дойдёт очередь по фазам, сделан один сквозной вертикальный
срез поперёк Фаз 1/2/4: минимальная SQLite-схема, Tauri-команда импорта,
выбор файла через нативный диалог, чат появляется в рельсе и открывается
в дашборде с тремя метриками (сводка, активность с авто-гранулярностью,
топ участников). Ниже это разнесено по своим фазам с пометкой, что именно
сделано в MVP-объёме, а что осталось для полной версии фазы.

## Фаза 1 — Импорт
1. ✅ Фикстуры `tests/fixtures/`: трёхдневный чат, переписка на двоих,
   группа на 50 (с deleted account, ботом, сервисными событиями, poll,
   location_information), чат без реакций, англоязычный чат. Форма — по
   разведке реального экспорта пользователя (только структура полей,
   никакого реального контента)
2. ✅ Стриминговый парсер `src-tauri/src/import/`: `parse_export()` читает
   `result.json` через `serde_json::Deserializer::from_reader` и кастомный
   `Visitor`/`DeserializeSeed` по полю `messages`, вызывает колбэк на
   каждое событие, не собирая `Vec` внутри себя. `text`/`text_entities`,
   `from_id`-идентичность, отсутствующие/числа-или-строки поля — по
   SPEC §8. Несмоделированные поля (poll, rich_message,
   inline_bot_buttons, contact_information, todo_list, game_*) уходят в
   `extra` через `#[serde(flatten)]`, не роняя парсер. 13 тестов
   (`cargo test`), `cargo clippy` чист. SQLite/Tauri-команда/UI — ещё нет,
   `parse_export()` пока ничем не вызывается кроме тестов
3. 🔶 SQLite (MVP-объём): миграция `0001` (`src-tauri/src/db/migrations/`)
   — только `chats`/`people`/`messages`, без `aliases`/`reactions`/
   `links`/`tokens` и без строк для сервисных событий (ни одна текущая
   метрика их не читает; понадобятся — миграция + повторный импорт,
   который уже поддержан как первоклассный сценарий). Одна транзакция на
   импорт, `person_id` резолвится через `HashMap` в памяти (не по числу
   сообщений), WAL, `chats.id` переживает повторный импорт того же
   `tg_chat_id`. Батчи по 5000 отдельными транзакциями, `spawn_blocking`
   с событием `ingest://progress` и отмена — не сделаны: вместо этого
   честная имитация «мгновенно для маленького файла» на фронте (таймер
   400 мс до показа «Импортируется…»). Настоящий прогресс — когда
   реально понадобится на большом файле
4. 🔶 Импорт (MVP-объём): нативный диалог выбора файла
   (`@tauri-apps/plugin-dialog`) реально wired на `ImportDropzone`,
   ошибки импорта показываются текстом. Отдельного экрана Импорта с
   прогресс-баром/ETA и состоянием «первый запуск» вне дроп-зоны (макет
   3c) — нет

## Фаза 2 — Библиотека чатов
🔶 Чат после импорта появляется в рельсе (имя, тип, счётчик сообщений),
клик открывает дашборд — минимум, чтобы MVP работал целиком. Полноценный
экран (карточки как в макете 3a, удаление, явный выбор при конфликте
`tg_chat_id` на старых экспортах без `id`) — не сделан, `LibraryEmptyState`
после первого импорта уступает место временной заглушке с числом чатов.

## Фаза 3 — Участники
🔲 Таблица `from_id` с алиасами, объединение похожих дублей, скрытие ботов
(макет 3d/3e). До метрик — merge меняет `person_id`, на который завязано
всё дальше.

## Фаза 4 — Дашборд, базовые метрики
🔶 Сделаны три метрики из «Базовых» — ровно секции 00/01/02 макета
«Дашборд» (вариант 2a): сводка (сообщений/слов/в день/участников),
активность с автогранулярностью (`src-tauri/src/metrics/granularity.rs`
— чистая функция, переиспользуется любой будущей time-series метрикой;
UTC, часовой пояс экспортёра не восстанавливается и честно помечен в UI),
топ участников с вырождением в соотношение для чата на двоих (§7).
Средняя длина сообщения — тем же запросом, не отдельная метрика.
Не сделаны: тепловая карта день×час (нужен отдельный 2D-компонент),
рекордный интервал/самая долгая тишина, частота правок (нужна колонка
`is_edited`, которой пока нет в схеме), период/фильтр участника/
переключатель чата с самого дашборда (секции 03/04 макета и полная версия
экрана из SPEC §10). Общий паттерн «метрика скрыта / показана с
оговоркой» (4 состояния из макета «Дизайн-токены» §5c) — не реализован
как переиспользуемый компонент, понадобится для первой скрываемой
метрики.

## Фаза 5 — Медиа
🔲 Голосовые (сумма/рекорд), топ доменов, `forwarded_from`, история
названий чата и участников.

## Фаза 6 — Социальная динамика
🔲 Граф ответов по `reply_to` (ожидаемое vs фактическое, не сырые
счётчики), медианное время ответа, кто начинает/хоронит разговор (порог
паузы от плотности чата), реакции, самый длинный монолог. Для чатов на
двоих — замена графа на баланс инициативы.

## Фаза 7 — Язык
🔲 Определение языка чата, стеммер/стоп-слова под него, «слово периода»
(log-odds, Monroe), «слово-визитка» (TF-IDF), топ эмодзи/стикеров, индексы
(смешливость/капс/мат). Таблица `tokens` строится по кнопке, лениво.

## Фаза 8 — Слайды

drag-and-drop, экспорт PNG через `html-to-image`, заголовки/разбивка
зависят от длины периода.
