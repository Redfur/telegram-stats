# План разработки

Верхнеуровневый план по фазам, в порядке зависимостей. Каждая фаза — один или несколько вертикальных срезов; перед стартом каждого показывается план и ждётся подтверждение (см. CLAUDE.md «Как я хочу работать»). Порядок фаз 0–3 жёсткий: без импорта и людей метрикам считать не над чем. Порядок 4–7 внутри себя подвижный и совпадает с `docs/SPEC.md` §9 («базовые → медиа → социальные → языковые»).

Статус: 🔲 не начато · 🔶 в работе · ✅ готово

**MVP-срез (сентябрь 2026).** По просьбе пользователя увидеть рабочий MVP раньше, чем дойдёт очередь по фазам, сделан один сквозной вертикальный срез поперёк Фаз 1/2/4: минимальная SQLite-схема, Tauri-команда импорта, выбор файла через нативный диалог, чат появляется в рельсе и открывается в дашборде с тремя метриками (сводка, активность с авто-гранулярностью, топ участников). Ниже это разнесено по своим фазам с пометкой, что именно сделано в MVP-объёме, а что осталось для полной версии фазы.

## Фаза 3 — Участники

🔶 Таблица участников с историческими именами (`aliases`, копится во время импорта — буфер по уникальным парам человек/имя, не по сообщениям), переименование, скрытие, объединение дублей (`merge_people` — мягкое удаление через `merged_into`, сообщения переезжают на «главного») и поиск по имени — общее ядро `ParticipantsManager` (`src/components/ParticipantsManager/`), макет 3d/3e. Используется в двух местах: шаг 3 мастера импорта (`ParticipantReviewStep` — модальный chrome, открывается после каждого успешного импорта) и самостоятельный экран «Участники» (`src/screens/Participants/`) — теперь реальный пункт нава, открывается для уже выбранного в рельсе чата (макет 3d: чат в рельсе и пункт нава подсвечены одновременно; повторный клик по чату в рельсе возвращает на дашборд). Метрики (`get_top_participants`, `get_chat_totals`, `list_chats`) фильтруют `merged_into IS NULL AND is_hidden = 0` и считают `participant_count` вживую, а не из снимка на момент импорта.

Не сделано: авто-детект похожих дублей/ботов, сегмент-фильтр «Все/Дубли/Боты/Скрытые» и сворачивание хвоста для больших чатов (макет 3e) — для них нет честного сигнала в текущих данных (нужен отдельный эвристический шаг детекции, которого нет).

Правка по фидбэку с реального использования (сентябрь 2026): переимпорт уже существующего в базе чата подвисал на этапе «Финализация» без ошибки и без реакции на «Отменить» (сама кнопка на этой фазе и раньше не действует — это ожидаемо, зависал сам импорт, а не UI). Баг существует с самого появления слияния участников в этой фазе, не связан с более поздним таймлайном (Фазой ниже). Причина — в цикле реконсиляции переимпорта (`db/import.rs`) `people` временного чата удаляются по одной (`DELETE FROM people WHERE id = ?`), и SQLite на каждое удаление гоняет неявную FK-проверку (`ON DELETE SET NULL`/`CASCADE`) по всем ссылающимся таблицам; `messages` — самая крупная таблица в приложении (потенциально миллионы строк по всем чатам сразу) — не имела отдельного индекса на голом `person_id` (только составной `(chat_id, person_id)`, где `chat_id` — ведущая колонка, бесполезный для проверки/запроса без него), так что каждое удаление участника гоняло полный скан ВСЕХ сообщений базы, не только текущего чата. На чате с большим числом участников это превращало реконсиляцию в многоминутное подвисание. Миграция `0013_person_fk_indexes.sql` добавляет недостающие индексы (`messages.person_id`, `reaction_actors.person_id`, `people.merged_into`); заодно явный `UPDATE messages ... WHERE person_id = ? AND chat_id = ?` в том же цикле получил предикат `chat_id`, которого не хватало (в отличие от `merge_people`, где он уже был) — теперь использует существующий составной индекс вместо скана.

✅ **Таймлайн участников** — секция 05 дашборда (макет «Дашборд», ход `t10`/вариант `10a` — «Таймлайн участников — схлопнутый»): сколько человек прошло через чат всего/сейчас/вышло, медианный срок пребывания, пик состава, история входов/выходов/удалений по каждому участнику (сегменты с промежутками при повторном входе), лента групповых событий (создание чата, смена названия/фото, миграция в супергруппу). Источник — сервисные сообщения экспорта (`type: "service"`, `action: "invite_members"/"remove_members"/"create_group"/...`), которые парсер читал и раньше (`ServiceEvent`), но нигде не сохранял («не персистятся в MVP») — этот срез первый их персистит, миграция `0011_timeline.sql` (`membership_events`/`chat_events`, флаг `chats.timeline_ready`). Как и реакции (Фаза 6) — данные доступны только на момент парсинга, self-heal невозможен, только переимпорт (`TimelineOverview::NeedsReimport`); «нечего показывать» (`NotApplicable` — личный чат, `saved_messages`, чат без единого события) определяется по факту отсутствия строк, не по `chats.chat_type` (эта строка не валидируется парсером). Объём данных (события на участника, не на сообщение) на порядки меньше `messages` — сводка считается вживую в Tauri-команде, без отдельных precompute-таблиц.

`members[]` в исходном экспорте — только отображаемые имена, без id (`from_id` есть только у `actor`, docs/SPEC.md §8.2): `person_id` резолвится по точному совпадению имени среди уже известных участников чата (`people.display_name` + вся история `aliases`), неоднозначное или ненайденное имя остаётся с `person_id = NULL` и сырым `unresolved_name` — честная деградация вместо угадывания, счётчик таких событий (`unresolved_event_count`) показывается в UI отдельной строкой-предупреждением. Участник с сообщениями, но без явного входа (история экспорта началась не с `create_group`, либо человек уже был в чате до видимого начала истории) не получает выдуманной даты входа — его сегмент открывается с момента его первого наблюдения, без совпадающей по времени точки в `events` (см. ниже); этот же момент участвует в ступенчатой композиции состава наравне с обычными `joined`-событиями — иначе пик состава считал бы только явно вошедших. Медианный срок и срок в капсуле наведённого участника считаются от `chats.last_msg_ts` (`as_of_ts`), не от системных часов — та же дисциплина, что и у остальных метрик проекта (период чата, не wall-clock).

**Объединённые участники (`merge_people`)**: правка по фидбэку сразу после первой версии — если у слитого аккаунта нет собственного `joined`-события (частый случай `since_start`), а `merge_people` при слиянии просто переносит `membership_events.person_id` на главного, то единственное событие «выход» слитого аккаунта вставало бы в общий ряд с `joined` аккаунта-приёмника и рвало линию на месте, даже если приёмник всё это время оставался в чате. Поэтому `merge_people` **не** переносит `membership_events`/`chat_events` (в отличие от `messages`/`reaction_actors`, которые переносит) — `get_participant_timeline` сама резолвит объединение на чтении: группирует сырые события по исходному `person_id` (`COALESCE(people.merged_into, people.id)`), считает покрытие для каждого бывшего аккаунта независимо (`build_coverage_segments`, `since_start`-допущение — только у аккаунта-приёмника, по объединённому первому сообщению), и только потом объединяет получившиеся интервалы одного участника в непрерывные отрезки (`union_segments` — тот же приём объединения интервалов, что и у самого покрытия, но уровнем выше). Итог соответствует ожиданию из фидбэка: если оба аккаунта в какой-то момент числились в чате одновременно — линия не рвётся; если между выходом одного и входом другого был настоящий разрыв — пунктир остаётся. Все резолвленные события (по всем объединённым аккаунтам) при этом видны как точки на линии независимо от того, сдвигают ли они границу объединённого сегмента (`PersonTimelineRow.events`, отдельно от `segments`).

Фронт (`src/components/TimelineBlock/`) — тот же паттерн `skeleton → UnavailableCard → контент`, что и у `ReactionsBlock`/`MessageTypesBlock`, с двумя разными исходами недоступности (`needs_reimport` — кнопка «Обновить выгрузку», `not_applicable` — без кнопки). `TimelineChart` — позиционированные `div`/один `SVG polyline` (ступенчатая линия состава), а не `recharts`: многострочный таймлайн с сегментами/промежутками/точками — нестандартная форма чарта, тот же приём, что и диаграмма-весы в `ReactionPersonFilter`. Точки событий рисуются из `person.events`, а не из границ `person.segments` — у объединённых аккаунтов событие может лежать внутри уже непрерывного покрытия. Цвет на участника — детерминированное присвоение по позиции строки из 8 категориальных слотов (`--series-1..8` в `tokens.css`, валидированы по методике скилла dataviz), с повтором цикла после 8-й строки — осознанное отступление от «не циклировать» категориальные цвета: идентичность здесь несёт в первую очередь позиция строки и имя в тултипе/капсуле, а не только цвет. Цвет сохраняется у всех участников, включая вышедших/удалённых (не гасится). Наведение на строку — выделение толщиной линии (чистый CSS `:hover`) и капсула с деталями в шапке блока (`TimelineHeader`, поднимается через `TimelineBlock`; шапка получила фиксированную минимальную высоту — без неё переключение капсула/сводка на каждый hover сдвигало блок под курсором и дёргало содержимое). Наведение на точку (вход/выход/удаление/групповое событие) — свой тултип (`TimelineChart`, состояние `tooltip`), не нативный `title`: в WebView нативные тултипы на маленьких абсолютно позиционированных точках срабатывали ненадёжно (не показывались, дёргали скролл) — заменено сразу, отдельного «известного ограничения» на этот счёт не заводим. Строки отсортированы по дате первого появления в чате (не по сроку пребывания — макет явно откладывает такую сортировку на будущее). Отдельного списка событий под таймлайном нет — вся информация о событиях доступна только через тултипы на точках и шапку (по правке пользователя при планировании этого среза).

Не в этом срезе: «by …» (кем приглашён/удалён) в капсуле наведённого участника — данные для этого есть в `membership_events.related_person_id`, но наружу в `TimelineSummary` не выведены; сортировка строк по сроку пребывания и подпись прямо на линии вместо толщины — сознательно отклонённые в этом ходе макета альтернативы (см. комментарий `dv-next` хода `t10`); лимит числа строк для очень больших групп (сотни участников) не заведён — таймлайн просто станет высоким и проскроллится, как уже сделано для таблицы обмена реакциями.

Правка по фидбэку сразу после первой версии: переимпорт уже существующего чата подвисал на этапе «Finalizing» без ошибки и без реакции на «Отменить» (сама кнопка задизейблена на этой фазе и раньше — это ожидаемо, зависал сам импорт). Причина — `membership_events`/`chat_events` ссылаются на `people(id)` тремя FK-колонками (`person_id`/`related_person_id`/`actor_id`) без собственного индекса (составной `(chat_id, person_id)` из `0011` для FK-проверки без `chat_id` бесполезен) — на переимпорте цикл слияния участников (`db/import.rs`) удаляет старые строки `people` по одной, и SQLite на каждое `DELETE` гоняет полный скан этих таблиц ради `ON DELETE SET NULL`; на чате с большим числом участников это превращало реконсиляцию в многоминутное подвисание без какого-либо признака жизни. Миграция `0012_timeline_indexes.sql` добавляет недостающие индексы (`0011` уже применена как минимум локально — вперёд-только, трогать её нельзя). Заодно найден и исправлен соседний баг: `membership_events`/`chat_events`, в отличие от `message_reactions`/`reaction_actors` (те каскадируют от `messages`, а `messages` для старой записи стирается явно), никогда не чистились для `old_id` на переимпорте — новые строки просто переезжали поверх старых, задваивая события на каждый повторный импорт; `db/import.rs` теперь стирает старые `membership_events`/`chat_events` явно, тем же местом, где стираются `messages`.

Оптимизация (вдогонку Фазе 4 — тем же приёмом): `get_people` подвисал на больших чатах отдельно от дашборда — раньше это был `LEFT JOIN messages` + `GROUP BY p.id` на каждое открытие экрана «Участники», не входивший в precompute-срез Фазы 4. Миграция `0007` добавила `person_message_stats.first_ts`/`last_ts`, `get_people` читает готовые `message_count`/`first_ts`/`last_ts` вместо скана `messages`; тот же `ensure_dashboard_ready` self-heal, что и у дашборда. `ParticipantsManager` получил `loading`-состояние (скелетон-строки) и debounce смены `chatId` на 150 мс — используется только самостоятельным экраном «Участники» (`Participants.tsx`/`usePeopleReview`), шаг мастера импорта (`ParticipantReviewStep`) в скелетоне не нуждается: `people` там уже посчитаны к моменту открытия шага (precompute — часть той же транзакции импорта).

## Фаза 4 — Дашборд, базовые метрики

🔶 Сделаны три метрики из «Базовых» — секции 00/01/02 макета «Дашборд» (вариант 2a): сводка (сообщений/слов/в день/участников), активность с автогранулярностью (`src-tauri/src/metrics/granularity.rs` — чистая функция, переиспользуется любой будущей time-series метрикой; UTC, часовой пояс экспортёра не восстанавливается и честно помечен в UI), топ участников с вырождением в соотношение для чата на двоих (§7). Средняя длина сообщения — тем же запросом, не отдельная метрика.

Плюс секция 03 — универсальный блок «Типы сообщений» (ход `t6` макета «Дашборд», см. `docs/SPEC.md` §9 «Типы сообщений»): переключатель на 13 типов (`text` — непустой текст, не эксклюзивен с медиа: фото с подписью считается и в «фото», и в «текст»; медиа: фото/стикер/голосовое/кружочек/видео/гифка/файл; флаги: пересланное/отредактированное/опрос/геометка/контакт) с бейджем-счётчиком, карточка сводки (две раскладки — частота с пиком/лидером для одиннадцати типов, длительность суммарно/медиана/максимум для голосовых/кружочков), гистограмма по выбираемому виду (месяц — абсолютный календарный бакет; день недели и час суток — распределения по всему периоду, не временные ряды: «по дням» показывает Пн–Вс, а не подряд идущие календарные даты, как в первой версии этого среза — переделано по правке пользователя; свой трёхуровневый выбор, не переиспользует `Granularity`) и таблица участников. «Пик»/«средний темп» в карточке сводки всегда считаются по абсолютному месяцу/дню — отдельная `RateGranularity`, не зависящая от того, что выбрано для самой гистограммы. Миграция `0004` добавила `messages.media_type`/`has_photo`/`has_file`/`has_poll`/`has_location`/`has_contact`/`forwarded_from`/`edited_ts`/`duration_seconds` и `chats.message_types_ready` (чаты, импортированные до этой фичи, показывают «Обновить выгрузку» вместо лживых нулей — тот же паттерн деградации, что и у отсутствующих `reactions` в старых экспортах). Реакции — сознательно не в этом срезе: нужна отдельная таблица `reactions` и это уже метрика Фазы 6, а не универсального блока (см. `docs/SPEC.md` §9). Мультивыбор типов для сравнения на одном графике и слайд «Типы сообщений» в наборе Фазы 8 — заявлены в самом макете как следующий шаг, не в этом срезе. `UnavailableCard` (`src/components/ui/`) — общий примитив для паттерна «метрика недоступна», заведён этим срезом, переиспользуется будущими метриками с опциональными требованиями к данным (§7).

Оптимизация: сводка/активность/топ участников больше не считаются вживую при каждом открытии чата — миграция `0005` добавила `chats.word_count`/`char_count`/`dashboard_ready`, таблицы `activity_buckets` (готовая гистограмма на выбранной гранулярности) и `person_message_stats` (счётчик/сумма длины по сырому `person_id`, без учёта merge/hide). `metrics::precompute::recompute_dashboard_metrics` считает их один раз в конце `import_into_db` (та же транзакция, что и остальные метаданные чата) — было наоборот: `get_chat_totals`/`get_activity_series`/`get_top_participants` каждый раз заново сканировали `messages`, из-за чего переключение между чатами в интерфейсе подтормаживало на больших чатах. В отличие от `message_types_ready` это не новая метрика, которую можно честно пометить «недоступна» — переключение чатов должно было работать всегда, поэтому чат, импортированный до этого среза (`dashboard_ready=0` по умолчанию), досчитывается лениво при первом чтении (`ensure_dashboard_ready`), а не требует явного переимпорта. `merge_people` физически переносит `messages.person_id` на `primary_id` — единственное действие вне импорта, способное расходиться с `person_message_stats`, поэтому пересчитывает её (и только её, полным проходом) сразу после слияния; `hide_person`/`rename_person` только правят `people` и precomputed-таблиц не касаются.

Та же оптимизация докатана и на разбор типов сообщений — миграция `0006` добавила `message_type_counts`/`message_type_time_buckets`/`message_type_durations`/`message_type_participant_stats`. `recompute_message_type_metrics` считает всё за 13 типов один раз в конце импорта (та же транзакция); `get_message_type_overview`/`get_message_type_detail` читают готовые строки вместо пяти последовательных сканов `messages` на каждый клик по пилюле. Гистограмма «по месяцам» и рейт-бакеты «по месяцам» — буквально одно и то же выражение группировки, поэтому не хранятся дважды; для чатов короче `MONTH_VIEW_MIN_SPAN_DAYS` темп считается по отдельному ключу `rate_day` (`TypeTimeView` не предлагает «по дням» как вид гистограммы). В отличие от `dashboard_ready` этот self-heal ключуется на существовании строк в `message_type_counts` (13 строк на чат, включая нулевые счётчики, поэтому пусто — значит не посчитано, без отдельного флага) и срабатывает только для чата с `message_types_ready = 1` — для чата, ещё не прошедшего актуальный импортер, ничего не меняется, это по-прежнему «Обновите выгрузку», а не частичные данные. `merge_people` пересчитывает `message_type_participant_stats` тем же приёмом, что и `person_message_stats` — единственная person-keyed таблица в этой группе.

Дальше выяснилось, что precompute не убирает фриз целиком: единственный `Mutex<Connection>` на всё приложение (`Db`) сериализовал вообще все команды — самосогреваемый пересчёт (`ensure_dashboard_ready`) для одного чата держал мьютекс на время полного скана и блокировал ЛЮБОЙ другой запрос, включая уже готовые чаты. `db::build_pool` (`r2d2`/`r2d2_sqlite`) заменил единственное соединение пулом — WAL допускает параллельных читателей, поэтому self-heal одного чата больше не блокирует остальные. Это вскрыло гонку: два конкурентных вызова `ensure_dashboard_ready` для одного ещё не посчитанного чата раньше были невозможны (один мьютекс), с пулом — вполне, и оба порождали DELETE+INSERT, которые могли перемежаться (`UNIQUE constraint failed` в `activity_buckets`, поймано новым тестом `tests/db_pool.rs` до фикса). `precompute::with_write_lock` оборачивает каждый пересчёт (`recompute_dashboard_metrics`, `recompute_message_type_metrics`, `recompute_message_type_participant_stats`) в `BEGIN IMMEDIATE`/`COMMIT`, если соединение сейчас не внутри чужой транзакции (`is_autocommit()` — внутри `import_into_db` пересчёт просто исполняется как есть, второй `BEGIN` там не нужен и не разрешён); конкурирующий вызов блокируется на `BEGIN` (`busy_timeout` в `build_pool` ждёт вместо мгновенной ошибки) и переигрывает пересчёт поверх уже зафиксированных данных — лишняя работа разово, не гонка.

Фронт: примитив `Skeleton` (`src/components/ui/Skeleton/`) — пульсирующий плейсхолдер, используется вместо «ничего не рендерим, пока данные не пришли» в `Dashboard.tsx` (карточки сводки, график активности, список участников) и `MessageTypesBlock.tsx` (пилюли типов + карточка деталей; при смене выбранного типа/вида старая карточка остаётся видна с приглушённой непрозрачностью, а не мигает в пустоту). Оба компонента дебаунсят смену `chatId` на `SWITCH_DEBOUNCE_MS` (150 мс) перед тем как бить invoke — быстрый скролл по списку чатов в рельсе больше не ставит в очередь запросы на каждый промежуточный чат, только на тот, где пользователь задержался.

Не сделаны: тепловая карта день×час (нужен отдельный 2D-компонент), рекордный интервал/самая долгая тишина, период/фильтр участника/переключатель чата с самого дашборда (секция 04 макета и полная версия экрана из SPEC §10).

## Фаза 6 — Социальная динамика

🔶 Первый срез — блок «Реакции» (секция 04 дашборда): агрегаты (всего реакций, топ эмодзи, доля сообщений с реакциями) и given/received по персонам («кто ставит»/«кому ставят»). `src-tauri/src/db/migrations/0008_reactions.sql` — `message_reactions`/`reaction_actors`/`message_reaction_previews` заполняются **во время импорта** (`db/import.rs`), не пересчитываются из `messages` задним числом (в отличие от `message_type_*` — Telegram нигде, кроме `reactions` на самом сообщении в экспорте, эту информацию не хранит), поэтому у чата, импортированного до этой миграции, self-heal невозможен, только переимпорт (`ReactionsOverview::NeedsReimport`, отличается от self-heal паттерна «Типов сообщений»). Отдельно — `ReactionsOverview::NotInExport`: чат прошёл актуальный импортер, но сам экспорт сделан старой версией Telegram Desktop без поля `reactions` вовсе (`chats.reactions_supported`, трекается по факту хотя бы одного `Some(reactions)` на любом сообщении, даже пустом) — повторный импорт того же файла тут не поможет, нужен более новый экспорт; фронт показывает разные сообщения для этих двух случаев (`UnavailableCard` без/с кнопкой «Обновить выгрузку»). `reaction_actors` — только известные реагировавшие из `recent`, который Telegram усекает: `message_reactions.known_actor_count` (`len(recent)`) против авторитетного `count` — если меньше, «кто ставит» в сводке занижен (`given_data_incomplete`, помечено в UI), «кому ставят» при этом остаётся точным (считается по `count`, не по `recent`). Текст сообщения нигде в БД не хранится (`messages` — только `text_len`/`word_count`) — превью для «самых залайканных сообщений» снимается один раз при импорте, только для сообщений с реакциями (`message_reaction_previews`), не для всех подряд. `merge_people` пересчитывает `reaction_person_stats` (обе стороны: `reaction_actors.person_id` и `messages.person_id` через join). `metrics::reactions` — precompute (`recompute_reaction_metrics`/`recompute_reaction_person_stats`) поверх сырых таблиц, обычный self-heal-паттерн, но только для производных агрегатов, не для самих сырых данных (см. выше). Не в этом срезе: «кто чей фанат» (пары person→person), разбивка по времени, отдельная метрика «самое залайканное сообщение» вне общего топа.

Правки по фидбэку с реального использования (тот же срез): миграция `0009_reaction_actor_emoji.sql` добавила `reaction_actors.kind`/`emoji`/`document_id` (сознательно опущены в `0008` как YAGNI, понадобились для фильтра «какой участник какие эмодзи ставит») — та же несамопочинающаяся природа сырых таблиц реакций, строки до `0009` остаются без разбивки до переимпорта. `ReactionPersonFilter` — селект по всем участникам чата (`get_people`, не только видимая топ-10), `get_reaction_person_breakdown` отдаёт given/received по конкретным эмодзи. `get_top_reacted_messages` добавил `content_label` (тип сообщения — «Фото»/«Голосовое сообщение»/etc) для сообщений без текста, вместо прочерка. Список эмодзи в сводке сворачивается до топ-10 с кнопкой «показать все». Текст в топе сообщений переносится по словам, добавлена дата (короткая + полная в title). Эмодзи-глифы получили явный CSS-стек системных цветных эмодзи-шрифтов — без него часть окружений (Linux/WebKit без `Noto Color Emoji`) не подставляет замену вовсе.

Редизайн под макет Design Sync («Дашборд», ход `t8`/`8a`-`8b` — «Реакции — плотный блок и селект участника»), заменивший часть решений из абзаца выше: два раздельных топ-10 списка given/received стали одной таблицей «Обмен реакциями» (`ReactionsSummary.exchange` — все участники с ненулевой активностью, без верхнего предела, с колонкой «Чаще ставит» — миграция `0010_reaction_favorite_emoji.sql`), список эмодзи в сводке — сеткой 4×N (топ-12, не топ-10), у сводки добавились 3 новых показателя (среднее на сообщение с реакцией, число разных эмодзи, концентрация топ-4). «Самые залайканные»: клик открывает сообщение в Telegram (`t.me/c/<tg_chat_id>/<tg_msg_id>`, только для супергрупп/каналов — `messages.tg_msg_id`, не rowid), рядом с текстом — разбивка по эмодзи (`TopReactedMessage.reactions`) и дата. `ReactionPersonFilter` пересел на **cmdk** (headless-комбобокс с поиском, новая зависимость) вместо нативного `<select>`, разбивка выбранного участника — диаграмма-весы give/receive по эмодзи вместо двух списков, с кнопкой сброса фильтра. - `ReactionEmojiList` — сводка из 4 показателей и сетка эмодзи 4×N (топ-12), «показать все» разворачивает остаток компактными чипами, не полными карточками. Глифы — явный стек системных цветных эмодзи-шрифтов (Oswald/Manrope не покрывают эмодзи-диапазон). **Известное ограничение**: на Linux/WebKitGTK (`pnpm tauri dev` в WSL2) шрифт может рисовать «тофу» — ни COLRv1 (Noto Color Emoji), ни OT-SVG (Twemoji Mozilla) не поддерживаются WebKit, а CBDT/битмап через FreeType непроверен и тяжёлый, решено не вендорить; на реальной целевой платформе (Windows, WebView2/Chromium) эмодзи корректны уже сейчас

Три состояния: обычное; «ни ставил, ни получал»; `given_total > 0` при пустой разбивке — реакции посчитаны до миграции `0009`, ссылка «переимпортируйте чат» — собственная защита от вранья нулями, в макете этого состояния нет

Клик открывает сообщение в Telegram через `openUrl` (`@tauri-apps/plugin-opener` — передача клика системному обработчику ссылки, не сетевой вызов)

`Skeleton` (`src/components/ui/Skeleton/`) и debounce 150 мс на смену `chatId` — тот же паттерн, что и в `MessageTypesBlock`/`Dashboard` (Фаза 4).

Правки по фидбэку сразу после редизайна: сетка эмодзи — исправлен баг раскрытия хвоста (раньше «показать все» превращало компактные чипы в подробные карточки вместо простого раскрытия); у «Баланс» вернулась объясняющая подпись и исправлено направление полосы (было перепутано); разбивка по участнику сворачивается до топ-10 эмодзи; лимит в таблице обмена снят целиком (были «пропадающие» люди).

🔲 Остальное: граф ответов по `reply_to` (ожидаемое vs фактическое, не сырые счётчики), медианное время ответа, кто начинает/хоронит разговор (порог паузы от плотности чата), самый длинный монолог. Для чатов на двоих — замена графа на баланс инициативы.

## Бэклог — доработки вне фазовой структуры

Список собран по фидбэку с реального использования (сентябрь 2026), не привязан к порядку фаз выше. Приоритет между оставшимися пунктами не зафиксирован.

1. ✅ **Переименование приложения.** Слово «archive» заменено на «stats» во всех трёх местах, где встречалось: заголовок окна и `productName` (`src-tauri/tauri.conf.json` — `productName` напрямую определяет имя `.exe`/NSIS-инсталлятора и ярлыка после установки, кастомного `bundle.nsis`-объекта в конфиге нет), `<title>` (`index.html`), брендинг рельса (`src/components/AppRail/AppRail.tsx`). Ярлык в Windows теперь «TG Stats». Не тронуты: `identifier` (`com.reefrax.telegram-stats`) и `name` в `package.json`/`Cargo.toml` — слова «archive» там не было, а смена `identifier` рискует сравнением версий у уже установленных копий, не запрошена отдельно.
2. ✅ **Белая вспышка при запуске.** Инлайн `<style>` в `<head>` `index.html` (хардкод `#0d0f11`, CSS-переменные из `tokens.css` на этом этапе ещё не подключены) + `backgroundColor` окна в `tauri.conf.json` — закрывают вспышку и до, и после появления WebView-документа. Полноценная светлая тема и подхват системной — по-прежнему не сделаны, задел под них не в этом срезе.
3. 🔲 **Метрики для чатов на двоих.** Проверено по коду (`src-tauri/src/metrics/`): единственное реализованное вырождение — `TopParticipants.degenerate` (`queries.rs`, `get_top_participants`, `participant_count <= 2` → фронт показывает соотношение вместо таблицы). Не проработаны: `top_sender`/таблица участников в `message_types.rs` и таблица `exchange` в `reactions.rs` — обе строятся одинаково независимо от числа участников, для двоих выглядят как вырожденная таблица на одну-две строки. Отдельно — «баланс инициативы»/«медианное время ответа», которые `docs/SPEC.md` §7 прямо называет заменой графа ответов для личных чатов, — модуля для них в `metrics/` нет вообще, это не полировка существующего, а недостающий срез Фазы 6. Нужен отдельный проход: для каждого блока дашборда решить, что показывать при `participant_count <= 2` (спрятать как малополезное / заменить на другое представление / оставить как есть), и отдельно — реализовать сами метрики диалога.
4. ✅ **Кастомный скролл.** Системный скроллбар нигде в проекте не был стилизован — добавлено одно глобальное правило в `src/styles/base.css` (`scrollbar-width`/`scrollbar-color` для Firefox, `::-webkit-scrollbar*` для Chromium/WebView2) под токены `--border`/`--text-faint` — покрывает все реальные зоны прокрутки (рельс чатов, библиотека, дашборд, таблица участников, пикер участника в реакциях) без точечных правок в каждом `.module.css`. Переживёт будущую светлую тему без правок — токены уже определены для обеих тем.
5. 🔲 **Проверка обновлений и автообновление.** Проверено: ничего из этого не подключено — `tauri-plugin-updater` нет ни в `src-tauri/Cargo.toml`, ни в `tauri.conf.json` (секции `plugins` нет вовсе), `updater`-permission нет в `capabilities/default.json`, `.github/workflows/release.yml` публикует только NSIS-инсталлятор без `latest.json`/подписи артефакта. Объём при реализации: (а) экран настроек — сейчас в приложении нет ни роута `/settings`, ни пункта в `AppRail`, заводить с нуля; (б) сам `tauri-plugin-updater` (Rust + JS API + capability) с тумблером в настройках; (в) релизный workflow — генерация и подпись `latest.json`; (г) отдельное решение, как опциональная проверка обновлений соотносится с правилом «никакой сети в рантайме» (`CLAUDE.md`) — трактовать как сетевой запрос по явному действию/согласию пользователя, а не фоновую телеметрию, но формулировку правила стоит уточнить, когда до этого дойдём. Отдельно — сам процесс установки новой версии: сейчас NSIS-инсталлятор сначала предлагает удалить старую версию, потом ставить новую — рабочий, но недружелюбный сценарий, посмотреть штатный upgrade-режим NSIS/Tauri без ручного удаления.
6. 🔲 **Доступ Claude к содержимому приложения из WSL2 + визуальная сверка с макетами.** Это ограничение окружения, а не задача в кодовой базе — `pnpm tauri dev` в WSL2 не даёт Claude способа посмотреть на реальное окно (см. память `project_no_gui_automation`: нет GUI-автоматизации, xdotool, sudo в этом контейнере). Решение (X11/screenshot-мост или другое) нужно искать на стороне окружения/тулинга, не в репозитории. После того как доступ появится — отдельный проход по всему интерфейсу и сверка с макетами Design Sync, известны небольшие расхождения/недоделки, конкретный список не собран.
7. 🔲 **Нейросетевые фичи и платный доступ.** Проработать, где в приложении уместны LLM-фичи (более глубокий разбор чата, карточки вида «кто больше всех сливался» и т.п.) и как разделить бесплатный/платный функционал — базовые метрики остаются у всех, доп. фичи (в т.ч. на нейросетях) — в платном слое. Прямо конфликтует с правилом «никакой сети в рантайме» в текущем виде — нужен отдельный продуктовый дизайн-заход (явный opt-in, свой http-клиент только для этой фичи, что происходит с данными чата при отправке во внешний API, модель распространения платного доступа для локального десктоп-приложения без бэкенда) прежде чем начинать реализацию — заход на уровне продукта, не только кода.
