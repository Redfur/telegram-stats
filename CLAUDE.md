# Telegram Chat Stats

Локальное десктопное приложение (Tauri 2 + React/TypeScript) для анализа экспортов
переписки Telegram. Универсальный инструмент: работает с любым чатом любого размера,
хранит несколько импортов одновременно. Полный спек: `docs/SPEC.md` — прочитай его
перед началом работы над любой новой фичей.

## Абсолютные правила

- **Никакой сети в рантайме.** Ни одного HTTP-запроса, ни телеметрии, ни шрифтов с CDN,
  ни автообновлений. Всё вендорится в бандл. Если задача выглядит так, будто требует
  сетевого вызова, — остановись и спроси.
- **Реальные данные чата не попадают в репозиторий.** Ни в фикстуры, ни в тесты,
  ни в примеры, ни в комментарии. Тестовые данные — только синтетические.
- **Никогда не грузить весь `result.json` в память.** Только потоковый парсинг.
- **Никаких запросов без фильтра по `chat_id`.** Импортов в базе много, они изолированы.

## Универсальность — не опция

Ничего не предполагай про входные данные. Чат может быть на двоих и на тысячу, ему
может быть три дня и пятнадцать лет, он может быть не на русском. Конкретно:

- Гранулярность времени вычисляется от длины периода, а не зашита в «годы»
- У каждой метрики объявлены требования к данным; если они не выполнены, метрика
  скрывается, а не рисует пустой график
- Пороги (пауза между разговорами, минимальная частота слова) считаются от плотности
  чата, а не задаются константой
- Язык определяется по содержимому, стеммер и стоп-слова подбираются под него

Новая метрика не считается готовой, пока не проверена на всём наборе фикстур
из `tests/fixtures/` — там намеренно лежат вырожденные случаи.

## Разделение ответственности

Rust делает всё тяжёлое: парсинг, запись в SQLite, агрегации. TypeScript только рисует.
Не переноси вычисление метрик в React — файлы бывают на несколько гигабайт.

## Команды

```
pnpm install        # установка зависимостей
pnpm tauri dev      # запуск в разработке
pnpm tauri build    # сборка
pnpm build          # tsc --noEmit + vite build (проверка типов фронта)
cargo test          # тесты Rust (в src-tauri/)
pnpm test           # тесты фронта
cargo clippy        # линт Rust (в src-tauri/), должен быть чистым
```

`cargo test` реально запускает тесты (см. `src-tauri/tests/`). `pnpm test` пока не
имеет конфигурации — фронт ещё не оброс тем, что стоит тестировать так, а не
только `tsc`. ESLint/Prettier в проекте нет; типы проверяются через `tsc`,
Rust отформатирован `cargo fmt`.

## Текущее состояние репозитория

Верхнеуровневый план по фазам и их статус — в `docs/PLAN.md`, держи его в
актуальном состоянии вместе с этим файлом.

Фаза 0 (фундамент интерфейса) закрыта: токены (`src/styles/tokens.css`,
`base.css`, `fonts.css`) и примитивы (`src/components/ui/`) портированы из
проекта Claude Design «Основа дашборда с вариациями» — визуального макета
всех экранов приложения плюс логотипа
(`https://claude.ai/design/p/e42d80bd-e424-4d0f-b659-f559dda4e095`).
Читается и пишется через `DesignSync` — это обычный `PROJECT_TYPE_PROJECT`
с вручную нарисованными `.dc.html`-страницами, а не design-system-проект,
под который заточен инструмент; правки туда — точечные (например, замена
шрифта across-the-board), никогда не полная перегенерация страницы, чтобы
не сломать формат канваса. Барлоу/Барлоу-Кондесед из макета заменены на
Oswald/Manrope (и там, и в коде) — у Барлоу нет кириллицы. Каркас собран
(`AppShell` + `AppRail`, `src/components/`), `App.tsx` — хост реальных
экранов. Библиотека реализована целиком (макет 3a —
`src/screens/Library/Library.tsx` + `LibraryCard`, макет 3b —
`LibraryEmptyState` для пустого состояния). Импорт — рабочий сквозной
флоу (диалог выбора файла → прогресс/ошибка → разбор участников →
дашборд, `src/components/ImportFlow/`), но целиком вызывается кнопками
из Библиотеки, не отдельным пунктом нава. «Участники» в рельсе — теперь
самостоятельный экран (`src/screens/Participants/`, ядро таблицы —
`src/components/ParticipantsManager/`, общее с шагом 3 мастера
импорта): открывается для уже выбранного в рельсе чата, чат и пункт
нава подсвечены одновременно (макет 3d), повторный клик по чату
возвращает на дашборд. Клик по «Импорт»/«Слайды» в рельсе по-прежнему
ведёт на общую заглушку `ComingSoon` — эти экраны вне мастера импорта
ещё не построены.

`src-tauri/src/import/` — стриминговый парсер `result.json`
(`parse_export()`, кастомный `Visitor` поверх `serde_json`, без
`struson`), тип чата из корня экспорта — открытая строка, не
валидируется (`docs/SPEC.md` §2 — список известных значений неполный).

**MVP-срез сделан поперёк фаз** (см. пометки в `docs/PLAN.md`): целиком
рабочий путь импорт → SQLite → дашборд, но в урезанном объёме каждой
затронутой фазы — сперва весь путь целиком, остальные метрики и экраны
добираются инкрементально. `src-tauri/src/db/` — схема (`chats`/`people`/
`messages`/`aliases`, миграции `0001`–`0004` через ручной
`PRAGMA user_version`, без `reactions`/`links`/`tokens` и без строк для
сервисных событий — ни одна метрика их пока не читает; `0002` добавляет
`chats.source_file_size` для честного агрегата в шапке Библиотеки,
`0003` — `people.merged_into`/`is_hidden` и таблицу `aliases` для шага
разбора участников, `0004` — `messages.media_type`/`has_photo`/`has_file`/
`has_poll`/`has_location`/`has_contact`/`forwarded_from`/`edited_ts`/
`duration_seconds` и `chats.message_types_ready` для блока «Типы
сообщений», `0005` — `chats.word_count`/`char_count`/`dashboard_ready` и
таблицы `activity_buckets`/`person_message_stats` для precompute сводки/
активности/топа участников), Tauri-команды (`import_chat`, `cancel_import`, `list_chats`,
`delete_chat`, `get_people`, `merge_people`, `hide_person`,
`rename_person`, `get_chat_totals`, `get_activity_series`,
`get_top_participants`, `get_message_type_overview`,
`get_message_type_detail`), диалог выбора файла
(`@tauri-apps/plugin-dialog`).
`delete_chat` полагается на `ON DELETE CASCADE` — удаляет строку `chats`,
`messages`/`people`/`aliases` уходят сами. Импорт шлёт `ingest://progress`
(байты прочитанного файла против `source_file_size`, throttled ~150 мс,
`CountingReader` в `db/import.rs`) и поддерживает отмену через
`AtomicBool`-флаг, проверяемый раз на сообщение — некоммит транзакции
чистит всё сам, без отдельной логики отката. Повторный импорт того же
`tg_chat_id` сопоставляет `people` по `tg_person_id` (не стирает и
перезаливает, как `messages`) — `merged_into`/`is_hidden`/алиасы
переживают повторную выгрузку того же чата; сообщения для уже
объединённого участника при реимпорте резолвятся сразу на актуального
«главного» через `merged_into`, а не оседают на строке, которую метрики
и так фильтруют. `src-tauri/src/metrics/granularity.rs` — чистая функция
выбора гранулярности по SPEC §7, переиспользуемая любой будущей
time-series метрикой. `participant_count` в `get_chat_totals`/
`get_top_participants`/`list_chats` считается вживую по `people`, а не из
денормализованного снимка на момент импорта — иначе merge/hide не
отражались бы в метриках. `src-tauri/src/metrics/message_types.rs` —
универсальный блок «Типы сообщений» (секция 03 дашборда, ход `t6` макета
«Дашборд», `docs/SPEC.md` §9 «Типы сообщений»): 13 типов (включая
`text` — непустой `text_len`, не эксклюзивен с медиа: фото с подписью
считается и в «фото», и в «текст»), свой трёхуровневый выбор гистограммы
(`TypeTimeView`: месяц — абсолютный календарный бакет; день недели и час
суток — распределения по всему периоду, а не временные ряды, поэтому
намеренно не переиспользует `Granularity`; «по дням» — именно день
недели, Пн-первый, не подряд идущие календарные даты). «Пик»/средний
темп в карточке сводки — отдельная `RateGranularity` (месяц/день,
абсолютные), не зависящая от того, что выбрано для самой гистограммы —
у «пика по дню недели» нет смысла. Две раскладки сводки
(частота/длительность). `chats.message_types_ready` отличает чат,
прошедший через актуальный импортер, от чата, который ждёт переимпорта
— фронт (`MessageTypesBlock`) в последнем случае показывает
`UnavailableCard` вместо лживых нулей. `src-tauri/src/metrics/precompute.rs`
— `recompute_dashboard_metrics` считает сводку/активность/топ участников
один раз в конце `import_into_db`, а не при каждом открытии чата
(`get_chat_totals`/`get_activity_series`/`get_top_participants` раньше
сканировали `messages` вживую на каждое переключение чата в интерфейсе —
тормозило на больших чатах). Это не новая метрика вроде типов сообщений,
поэтому чат, импортированный до этого среза, не показывает «недоступно»,
а лениво досчитывается при первом чтении (`ensure_dashboard_ready`,
идемпотентно). `merge_people` физически переносит `messages.person_id` на
`primary_id`, из-за чего `person_message_stats` пересчитывается сразу
после слияния — единственное место вне импорта, где precomputed-данные
могут разойтись с `messages` (`hide_person`/`rename_person` таблиц не
касаются, они только правят `people`). Та же оптимизация докатана и на
`message_types.rs` — `recompute_message_type_metrics` считает
`message_type_counts`/`message_type_time_buckets`/`message_type_durations`/
`message_type_participant_stats` (13 типов) один раз в конце импорта;
`get_message_type_overview`/`get_message_type_detail` читают готовые
строки вместо пяти последовательных сканов `messages` на каждый клик по
пилюле. Self-heal здесь ключуется не на отдельном флаге, а на
существовании строк в `message_type_counts` (пересчёт всегда пишет все
13, включая нулевые — пусто однозначно значит «не посчитано») и
срабатывает только при `message_types_ready = 1`, иначе поведение не
меняется (`UnavailableCard`, как и раньше). `merge_people` дополнительно
пересчитывает `message_type_participant_stats` (единственная
person-keyed таблица в этой группе) тем же приёмом, что и
`person_message_stats`.

Precompute не убрал фриз целиком: `Db` был единственным `Mutex<Connection>`
на всё приложение, поэтому self-heal-пересчёт одного чата держал мьютекс
и блокировал вообще все остальные запросы, включая уже готовые чаты —
именно так ловился полный фриз при быстром переключении. `db::build_pool`
(`r2d2`/`r2d2_sqlite`) заменил его пулом соединений к тому же файлу; `Db`
теперь `pub struct Db(pub DbPool)`, команды берут соединение через
`db.0.get()`, а не `db.0.lock()`. Миграции по-прежнему прогоняются один
раз через `open_and_migrate` на отдельном соединении до сборки пула. Это
вскрыло гонку: `metrics::precompute::with_write_lock` оборачивает каждый
пересчёт (`recompute_dashboard_metrics`/`recompute_message_type_metrics`/
`recompute_message_type_participant_stats`) в `BEGIN IMMEDIATE`/`COMMIT`,
если соединение не внутри чужой транзакции (`Connection::is_autocommit`)
— иначе два конкурентных self-heal одного и того же непосчитанного чата
(два разных соединения из пула вместо одного мьютекса) перемежают свои
DELETE/INSERT и ловят `UNIQUE constraint failed` (тест
`tests/db_pool.rs` воспроизводит это до фикса, 6 потоков конкурентно
досчитывают один чат). `busy_timeout` в `build_pool` — конкурирующая
транзакция ждёт вместо мгновенной ошибки "database is locked". 46
Rust-тестов зелёные, `cargo clippy` чист.

Фронт: `Skeleton` (`src/components/ui/Skeleton/`) — пульсирующий
плейсхолдер, заменил «ничего не рендерим, пока данные не пришли» в
`Dashboard.tsx`/`MessageTypesBlock.tsx`. Оба компонента дебаунсят смену
`chatId` на 150 мс перед invoke — быстрый скролл по списку чатов в
рельсе больше не ставит в очередь запросы на каждый промежуточный чат.
ETA в прогрессе импорта, параллельные импорты, явный выбор при конфликте
`tg_chat_id` без `id` в старом экспорте, авто-детект дублей/ботов в шаге
разбора участников и остальные метрики из SPEC §9 — сознательно не в
этом срезе, см. `docs/PLAN.md`.

`tauri.conf.json` имеет `security.csp: null` (нужно будет задать CSP по
требованию из §4 `docs/SPEC.md`).

## Конвенции

- Ошибки в Rust — `thiserror` для типов, `anyhow` только на границе Tauri-команд
- Никаких `unwrap()` на пользовательских данных: экспорт Telegram бывает битым
  и разных версий; отсутствующее поле — норма, а не повод для паники
- Tauri-команды возвращают `Result<T, String>`, ошибки понятны пользователю,
  а не стектрейс
- Каждая метрика — самостоятельный модуль с тестами на фикстурах
- Миграции SQLite нумерованные, вперёд-только

## Фронтенд

- Примитивы интерфейса — React-компоненты с CSS-модулями
  (`src/components/ui/<Имя>/<Имя>.tsx` + `<Имя>.module.css`), а не голые
  CSS-классы. Глобальными остаются только `tokens.css` (переменные),
  `fonts.css` и типографские утилиты без состояния в `base.css`
  (`.kick`/`.sec`/`.num`) — заводить им React-обёртку не нужно, это не
  компоненты
- Для сложных/стейтфул-компонентов (таблицы, диалоги, поповеры, селекты,
  табы) — готовая headless/unstyled библиотека, а не написанное с нуля.
  Таблицы — `@tanstack/react-table` (заголовок `.table` в
  `DataTable.module.css`, логика — библиотека). Для следующего такого
  компонента сначала ищи headless-библиотеку с нужной логикой (например,
  Radix UI primitives для диалогов/поповеров/селектов) и стилизуй её под
  токены — не изобретай a11y и state machine заново
- В целом: готовое решение предпочтительнее самодельного, если оно не тянет
  сеть в рантайме (только сборка/dev-время) и укладывается в дизайн-систему
  без борьбы с её стилями «из коробки» (headless — да, готовый визуальный
  kit со своей темой — нет)
