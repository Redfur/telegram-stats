# Telegram Chat Stats

Локальное десктопное приложение (Tauri 2 + React/TypeScript) для анализа экспортов переписки Telegram. Универсальный инструмент: работает с любым чатом любого размера, хранит несколько импортов одновременно. Полный спек: `docs/SPEC.md` — прочитай его перед началом работы над любой новой фичей.

## Абсолютные правила

- **Никакой сети в рантайме.** Ни одного HTTP-запроса, ни телеметрии, ни шрифтов с CDN, ни автообновлений. Всё вендорится в бандл. Если задача выглядит так, будто требует сетевого вызова, — остановись и спроси.
- **Реальные данные чата не попадают в репозиторий.** Ни в фикстуры, ни в тесты, ни в примеры, ни в комментарии. Тестовые данные — только синтетические.
- **Никогда не грузить весь `result.json` в память.** Только потоковый парсинг.
- **Никаких запросов без фильтра по `chat_id`.** Импортов в базе много, они изолированы.

## Универсальность — не опция

Ничего не предполагай про входные данные. Чат может быть на двоих и на тысячу, ему может быть три дня и пятнадцать лет, он может быть не на русском. Конкретно:

- Гранулярность времени вычисляется от длины периода, а не зашита в «годы»
- У каждой метрики объявлены требования к данным; если они не выполнены, метрика скрывается, а не рисует пустой график
- Пороги (пауза между разговорами, минимальная частота слова) считаются от плотности чата, а не задаются константой
- Язык определяется по содержимому, стеммер и стоп-слова подбираются под него

Новая метрика не считается готовой, пока не проверена на всём наборе фикстур из `tests/fixtures/` — там намеренно лежат вырожденные случаи.

## Разделение ответственности

Rust делает всё тяжёлое: парсинг, запись в SQLite, агрегации. TypeScript только рисует. Не переноси вычисление метрик в React — файлы бывают на несколько гигабайт.

## Команды

```
pnpm install        # установка зависимостей
pnpm tauri dev      # запуск в разработке
pnpm tauri build    # сборка
pnpm build          # tsc --noEmit + vite build (проверка типов фронта)
cargo test          # тесты Rust (в src-tauri/)
pnpm test           # тесты фронта
cargo clippy        # линт Rust (в src-tauri/), должен быть чистым
```

`cargo test` реально запускает тесты (см. `src-tauri/tests/`). `pnpm test` пока не имеет конфигурации — фронт ещё не оброс тем, что стоит тестировать так, а не только `tsc`. ESLint/Prettier в проекте нет; типы проверяются через `tsc`, Rust отформатирован `cargo fmt`.

## CI/CD

- `.github/workflows/ci.yml` — на push в `main` и на PR: типчек + `vite build` фронта, `cargo fmt --check`/`cargo clippy -D warnings`/`cargo test` Rust-части (джобы `rust-lint`/`rust-test` идут параллельно друг другу и фронту). Всё на `ubuntu-latest`.
- `.github/workflows/build.yml` — только по ручному `workflow_dispatch`, реальная Windows-сборка (`pnpm tauri build`), NSIS-инсталлятор уходит в `actions/upload-artifact` на 14 дней без публикации. Версия получает суффикс `-dev.<короткий SHA>` (только в checkout раннера, не коммитится) — dev-сборка отличима от релизной и в имени файла, и в самом приложении.
- `.github/workflows/release.yml` — по тегу `v*.*.*`, на `windows-latest` (собирает реальный шипуемый бинарник). Сверяет тег с `version` в `tauri.conf.json` и падает при расхождении; читает секцию нужной версии из `CHANGELOG.md` (`mindsers/changelog-reader-action`, `validation_level: error`) и падает, если её нет — см. «Changelog» ниже; публикует **черновик** GitHub Release (NSIS-инсталлятор, тело — из changelog).
- Версия синхронизируется вручную в 4 местах: `package.json`, `Cargo.toml`, `tauri.conf.json`, секция `[x.y.z]` в `CHANGELOG.md`. Обе проверки в `release.yml` (тег и changelog) ловят забытый бамп хотя бы одного из них.
- В приложении сознательно нет проверки обновлений — это был бы сетевой запрос в рантайме (см. «Абсолютные правила»); сверка версии с GitHub Releases — вручную. Текущая версия показывается в подвале `AppRail` (`useAppVersion`, `src/hooks/useAppVersion.ts` — чтение метаданных бинарника, не сеть).

## Текущее состояние репозитория

Фазы 0–3 (интерфейс, импорт, библиотека чатов, участники) закрыты. Фаза 4 (дашборд, базовые метрики) и Фаза 6 (социальная динамика — блок «Реакции») — в работе. Что именно сделано в каждой фазе и почему — в `docs/PLAN.md`; держи его в актуальном состоянии вместе с этим файлом.

## Конвенции

- Ошибки в Rust — `thiserror` для типов, `anyhow` только на границе Tauri-команд
- Никаких `unwrap()` на пользовательских данных: экспорт Telegram бывает битым и разных версий; отсутствующее поле — норма, а не повод для паники
- Tauri-команды возвращают `Result<T, String>`, ошибки понятны пользователю, а не стектрейс
- Каждая метрика — самостоятельный модуль с тестами на фикстурах
- Миграции SQLite нумерованные, вперёд-только
- Метрику, которую можно пересчитать из уже сохранённых данных (агрегат), самопочиняем лениво при первом чтении, ключуясь по возможности на существовании строк, а не на отдельном флаге (пример — `ensure_dashboard_ready` в `metrics::precompute`). Пересчёт всегда идёт через `with_write_lock`: БД — пул соединений (`r2d2`), не мьютекс, поэтому конкурентный self-heal одного и того же чата — рабочий случай, а не гонка
- Данные, которые Telegram отдаёт только во время самого парсинга и нигде не хранит повторно (например сырые таблицы реакций) — self-heal для них невозможен в принципе, только переимпорт. UI различает это явно — `UnavailableCard` с кнопкой «Обновить выгрузку» и без
- Агрегаты вроде `participant_count` считаются вживую по `people`, а не из снимка на момент импорта — иначе merge/hide не отражались бы в метриках
- Повторный импорт того же `tg_chat_id` сопоставляет `people` по `tg_person_id`, а не стирает и перезаливает — `merged_into`/`is_hidden`/алиасы переживают переимпорт

## Changelog

Ведётся в `CHANGELOG.md` (корень репозитория) по формату [Keep a Changelog](https://keepachangelog.com/ru/1.1.0/) + [SemVer](https://semver.org/lang/ru/) — версии и так уже синхронизируются вручную между `package.json`/`Cargo.toml`/`tauri.conf.json` (см. «CI/CD» выше).

- Обязательный этап, не отдельная задача «потом»: любой коммит, меняющий пользовательское поведение (новая функция, фикс, breaking change), добавляет запись под `## [Unreleased]` **в том же коммите**. Внутренние изменения без видимого пользователю эффекта (рефакторинг, тесты, CI, документация без пользовательского эффекта) — записи не требуют.
- Категории — только реально использующиеся: Добавлено / Изменено / Устарело / Удалено / Исправлено / Безопасность. Пустые не заводятся.
- При бампе версии (сейчас ручной, три файла) `## [Unreleased]` переименовывается в `## [x.y.z] - YYYY-MM-DD`, над ним заводится новый пустой `## [Unreleased]` — тем же коммитом, что и сам бамп.
- `release.yml` на релизе читает секцию нужной версии из `CHANGELOG.md` (`mindsers/changelog-reader-action`, `validation_level: error`) и использует её как тело GitHub Release — если секции нет или она не по формату, релиз падает до сборки. Черновик (`draft: true`) всё равно остаётся редактируемым перед публикацией.

## Фронтенд

- Примитивы интерфейса — React-компоненты с CSS-модулями (`src/components/ui/<Имя>/<Имя>.tsx` + `<Имя>.module.css`), а не голые CSS-классы. Глобальными остаются только `tokens.css` (переменные), `fonts.css` и типографские утилиты без состояния в `base.css` (`.kick`/`.sec`/`.num`) — заводить им React-обёртку не нужно, это не компоненты
- Для сложных/стейтфул-компонентов (таблицы, диалоги, поповеры, селекты, табы) — готовая headless/unstyled библиотека, а не написанное с нуля. Таблицы — `@tanstack/react-table` (заголовок `.table` в `DataTable.module.css`, логика — библиотека). Для следующего такого компонента сначала ищи headless-библиотеку с нужной логикой (например, Radix UI primitives для диалогов/поповеров/селектов, cmdk для комбобоксов с поиском) и стилизуй её под токены — не изобретай a11y и state machine заново
- В целом: готовое решение предпочтительнее самодельного, если оно не тянет сеть в рантайме (только сборка/dev-время) и укладывается в дизайн-систему без борьбы с её стилями «из коробки» (headless — да, готовый визуальный kit со своей темой — нет)
- `Skeleton` (`src/components/ui/Skeleton/`) — стандартный пульсирующий плейсхолдер на время загрузки; debounce ~150 мс на смену `chatId` перед invoke — стандартный паттерн для любого нового per-chat блока дашборда, чтобы быстрый скролл по списку чатов не ставил в очередь запросы на каждый промежуточный чат
- Правки в проект Claude Design («Основа дашборда с вариациями», читается и пишется через `DesignSync`) — точечные (например, замена шрифта across-the-board), никогда не полная перегенерация `.dc.html`-страницы — это сломает формат канваса
